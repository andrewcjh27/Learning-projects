Lesson 01
REST Fundamentals
HTTP methods, status codes, headers, and the stateless request/response model that powers the modern web.

HTTP Methods & Semantics

GET retrieves a resource — safe, idempotent, no body. POST creates a new resource — not idempotent, body required. PUT replaces a resource entirely. PATCH applies a partial update. DELETE removes a resource.

Idempotency

An operation is idempotent if calling it N times produces the same result as calling it once. GET, PUT, and DELETE are idempotent. POST is not — submitting a payment form twice charges the card twice.

Statelessness

Each HTTP request must carry all the information needed to process it. The server holds no session state between requests — authentication tokens, pagination cursors, and context all travel in the request itself.

A 429 Too Many Requests response should always include a Retry-After header so clients know how long to wait before retrying.

Key Headers

  • Content-Type: application/json — body format being sent
  • Accept: application/json — format the client can handle
  • Authorization: Bearer <token> — authentication credential
  • Retry-After: 60 — seconds until rate limit resets

Status Code Reference

Request succeeded — GET response with body, or PUT/PATCH update applied
201 Created
POST succeeded and a new resource was created; Location header points to it
400 Bad Request
Malformed syntax — the server cannot even parse the request
401 Unauthorized
No valid credentials — send your Authorization header
403 Forbidden
Authenticated but not allowed — you don't have permission for this resource
404 Not Found
Resource doesn't exist at this URL
422 Unprocessable
Syntax valid but data failed validation (wrong type, missing required field)
429 Too Many Requests
Rate limit exceeded — check Retry-After header before retrying
500 Internal Server Error
The server crashed — not the client's fault
Lesson 02
FastAPI Basics
Python type hints become validation, OpenAPI docs, and async route handlers — all with minimal boilerplate.

What is FastAPI?

FastAPI is a Python web framework for building APIs. You write Python functions, decorate them with @app.get("/path") or @app.post("/path"), and FastAPI handles routing, request parsing, validation, and response serialisation. It auto-generates interactive API docs (Swagger UI) directly from your code — no separate documentation needed.

Why FastAPI?

FastAPI uses Python type hints to automatically validate request data, generate OpenAPI/Swagger docs, and produce helpful error messages. It is built on Starlette and Pydantic, and supports async def handlers natively.

Core Concepts

  • @app.get("/users") — decorator registers the route and HTTP method
  • Path parameters — /users/{user_id} captured in function args
  • Query parameters — ?skip=0&limit=20 declared as typed args with defaults
  • Pydantic models — class UserIn(BaseModel) for request/response validation
  • HTTPException(status_code=404) — raise to return error responses
  • Depends() — dependency injection for auth, DB sessions, etc.

FastAPI auto-generates /docs (Swagger UI) and /redoc from your type hints — interactive documentation is a free side effect of writing typed code.

async def vs def

Use async def for route handlers that call await (database queries, HTTP calls). Use plain def for CPU-bound work — FastAPI runs it in a thread pool automatically.

Lesson 03
Auth: OAuth 2.0 & JWT
Who are you, and what are you allowed to do? Understand tokens, signatures, and OAuth flows.

Authentication vs Authorisation

Authentication proves identity ("who are you?"). Authorisation enforces permissions ("what can you do?"). A JWT handles both — the payload identifies the user and carries their roles.

JWT Structure

A JWT is three base64url-encoded sections joined by dots: header.payload.signature. The header declares the algorithm. The payload contains claims: sub (subject/user id), exp (expiry), iat (issued at), roles.

Signature Verification

The server signs base64(header) + "." + base64(payload) using a secret key. To verify, re-compute the signature and compare — if they match, the payload has not been tampered with. The payload is readable by anyone; only the signature proves integrity.

Never store sensitive data in a JWT payload — it is base64url encoded, not encrypted. Anyone with the token can decode and read it.

OAuth 2.0 Flows

  • Client Credentials — machine-to-machine; app authenticates with client_id + secret, gets access token
  • Authorization Code — user login; browser redirect to provider, user consents, code exchanged for tokens
  • Bearer token — Authorization: Bearer <jwt> on every subsequent request

Lesson 04
Rate Limiting & Pagination
Protect your API from abuse and return large datasets in manageable, consistent chunks.

Rate Limiting

Rate limiting prevents any single client from overwhelming your server. When a client exceeds the limit, respond with 429 Too Many Requests and include a Retry-After header (seconds or HTTP date) so the client knows when to retry.

Algorithms

  • Fixed window — count requests in fixed time buckets (e.g. 100/minute). Simple but allows bursts at window boundaries.
  • Token bucket — tokens refill continuously at a steady rate. Smoother, allows short bursts up to bucket capacity.
  • Sliding window — hybrid; smoothes the boundary problem of fixed windows.

Pagination Strategies

Offset/limit (?page=2&limit=20) is simple but unreliable — inserting a row shifts all subsequent pages. Cursor-based (?cursor=abc123) uses an opaque pointer to the last seen item, making it stable even when data changes.

Always include total, has_more, and next_cursor (or next link) in paginated responses. Never return an unbounded list — set a max limit server-side.

Keyset Pagination

Filter by a sortable column: WHERE created_at < :last_seen ORDER BY created_at DESC LIMIT 20. Fast even on huge tables because it uses an index, unlike OFFSET which scans and skips rows.

Lesson 05
API Design Best Practices
Resource naming, versioning, error formats, and backward compatibility — the conventions that make APIs a pleasure to consume.

Resource Naming

Use nouns, not verbs. The HTTP method is the verb. /users not /getUsers. Use plural nouns: /events, /orders. Nest related resources: /users/{id}/posts.

Versioning

Put the version in the URL path: /v1/users. When you need to make breaking changes, introduce /v2/ and maintain both until clients migrate. Alternative: Accept: application/vnd.api+json;version=2 header versioning.

Consistent Error Format

Always return errors in the same shape:

  • {"error": {"code": "VALIDATION_ERROR", "message": "...", "details": [...]}}
  • Machine-readable code, human-readable message, actionable details

Backward compatibility rule: you may add new fields to responses and new optional fields to requests. Never remove or rename existing fields — that is a breaking change requiring a new API version.

Idempotency Keys

For non-idempotent POST operations (payments, order creation), accept an Idempotency-Key header. If the client retries with the same key, return the original response instead of creating a duplicate.

Beginner
URL Shortener API
2 routes · Pydantic models · path parameters · 301 redirect
▸

Build a minimal URL shortener. A client POSTs a long URL and gets back a short code. A GET request with that code returns a 301 redirect to the original URL.

1
Define your Pydantic models
The request body needs a url field. The response returns the short code and the full short URL.
from pydantic import BaseModel, HttpUrl class ShortenRequest(BaseModel): url: HttpUrl # validates it's a real URL class ShortenResponse(BaseModel): code: str # e.g. "aB3xZ9" short_url: str # e.g. "https://sho.rt/aB3xZ9" original_url: str
2
POST /shorten — create a short link
Generate a random 6-character code, store it in a dict (or DB), return the response model.
import secrets from fastapi import FastAPI from fastapi.responses import RedirectResponse app = FastAPI() db: dict[str, str] = {} # code → original_url @app.post("/shorten", response_model=ShortenResponse, status_code=201) async def shorten(body: ShortenRequest): code = secrets.token_urlsafe(6)[:6] db[code] = str(body.url) return ShortenResponse( code=code, short_url=f"https://sho.rt/{code}", original_url=str(body.url) )
3
GET /{code} — redirect to original URL
Look up the code. Return 301 Moved Permanently so browsers follow it automatically.
@app.get("/{code}") async def redirect(code: str): url = db.get(code) if not url: raise HTTPException(status_code=404, detail="Code not found") return RedirectResponse(url=url, status_code=301)
4
Try it — open the HTTP builder on Lesson 1
Switch to a POST request, set the body to {"url": "https://example.com/very/long/path"}, and expect a 201 response with the short code. Then do a GET with the code and expect a 301.
What you practised: Pydantic's HttpUrl validator, status_code=201 on POST, RedirectResponse, and path parameters for lookup.

import jwt, datetime @app.post("/auth/login") async def login(body: UserIn): hashed = users_db.get(body.username) if not hashed or not pwd_ctx.verify(body.password, hashed): raise HTTPException(401, "Bad credentials") payload = { "sub": body.username, "exp": datetime.utcnow() + timedelta(hours=1) } token = jwt.encode(payload, SECRET_KEY, algorithm="HS256") return {"access_token": token, "token_type": "bearer"}
