Why Distributed Computing?
Single machines hit hard limits. Distributed systems let you scale out — but introduce new trade-offs.

Scale-Up vs Scale-Out

Scale-up (vertical): buy a bigger machine — more RAM, more cores, faster disk. Limits: even the biggest server has bounded RAM and CPU; cost grows super-linearly; single point of failure.

Scale-out (horizontal): add more machines. Commodity hardware, fault-tolerant, theoretically unlimited. Trade-off: you now have a distributed system — and distributed systems are hard.

  • RAM limit: a 1 TB table can't fit in 256 GB RAM on one machine
  • CPU limit: 96-core server still can't train a 70B parameter model in reasonable time
  • I/O bottleneck: one disk ≈ 500 MB/s; 1000 disks = 500 GB/s

CAP Theorem

In a distributed system you can guarantee at most 2 of 3 properties:

  • Consistency: every read gets the most recent write (or an error)
  • Availability: every request receives a (non-error) response
  • Partition Tolerance: system works even when network drops messages between nodes

Network partitions are inevitable in any real distributed system. You must choose between consistency and availability when a partition occurs.

Latency Reality

Each network hop adds 0.5–5 ms. A query hitting 10 services could add 50 ms of pure network overhead. Minimise cross-rack traffic; prefer co-located data.

Key Terms

CAPostgreSQL, MySQL — sacrifice partition tolerance (single-region)
CPHBase, Zookeeper — sacrifice availability during partitions
APCassandra, DynamoDB — sacrifice consistency (eventual consistency)
PartitionNetwork failure causing nodes to lose communication

Lesson 02 of 05
Apache Spark
Distributed in-memory computation. Lazy transformations, DAG execution, and the magic of partitioning.

What is Spark?

Spark is a distributed in-memory computation engine. Data is split across many machines; Spark coordinates parallel processing across all of them, keeping intermediate results in RAM for speed.

RDDs → DataFrames

  • RDD: low-level API; a distributed collection of objects. Fault-tolerant via lineage.
  • DataFrame: tabular, schema-aware, optimised by Catalyst query optimiser — use these in practice.
  • Dataset: type-safe DataFrames (Scala/Java only).

Lazy Evaluation

Transformations (map, filter, join, groupBy) are lazy — they build a query plan but execute nothing. Only an action triggers execution:

  • .count(), .collect(), .show()
  • .write.parquet(...)
  • .first(), .take(n)

Catalyst optimiser can reorder and prune operations across the lazy plan before execution — predicate pushdown, column pruning, etc.

Partitioning & Shuffle

Data is split into N partitions, each processed in parallel on a different executor. The expensive operation is the shuffle: data moves between executors for join or groupBy, requiring network I/O.

ShuffleAll-to-all data exchange — triggers a new stage

Lesson 03 of 05
Apache Kafka
Distributed message log for event streaming, service decoupling, and real-time data pipelines.

Kafka Fundamentals

Kafka is a distributed commit log. Messages are appended to an ordered, immutable log — never overwritten, retained for days or weeks.

  • Topic: named stream of records (like a database table)
  • Partition: a topic is split into N partitions — each an ordered log on a different broker
  • Offset: position of a message in a partition (monotonically increasing)
  • Producer: writes messages; chooses partition via key hash or round-robin
  • Consumer: reads from a specific offset; tracks its own position

Consumer Groups

Multiple consumers can form a consumer group. Kafka assigns each partition to exactly one consumer in the group — preventing duplicate reads. More consumers than partitions = idle consumers.

Key Properties

  • Retention: messages kept for N days regardless of consumption
  • At-least-once: default; consumer may re-read on failure
  • Exactly-once: via transactions — higher overhead
  • CDC: Change Data Capture — stream DB changes via Kafka Connect

Partition rebalancing occurs when consumers join/leave the group. Briefly pauses consumption — design for it.

Use Cases

Event streamingClickstreams, IoT sensor data, user activity
DecouplingProducer doesn't need to know about consumers
CDCReplicate DB changes to data warehouse in real time
Real-time analyticsFeed Flink/Spark Streaming for live dashboards

Lesson 04 of 05
Batch vs Streaming
Choose the right processing paradigm. Understand windowing strategies for time-series event streams.

Batch Processing

Accumulate data, then process it at intervals (hourly, daily). Simpler — standard SQL/Spark jobs. Higher latency: results may be hours old. Best for reporting, training ML models, large aggregations.

Stream Processing

Process each event as it arrives — latency in milliseconds. Complex: stateful operations, out-of-order events, exactly-once semantics. Use Apache Flink (true streaming) or Spark Structured Streaming (micro-batch).

Architectures

  • Lambda: batch layer (accurate, slow) + speed layer (fast, approximate) + serving layer
  • Kappa: streaming only — reprocess by replaying Kafka topic

Windowing

Group events into finite buckets for aggregation. Three main types:

  • Tumbling: fixed, non-overlapping windows — every event in exactly one window
  • Sliding: fixed size but moves by slide interval — events can be in multiple windows
  • Session: variable-length windows defined by gaps in activity

Watermarks define how long to wait for late-arriving events before closing a window. Late data after the watermark is dropped or handled via side outputs.

Comparison

LatencyBatch: minutes–hours · Streaming: milliseconds
ComplexityBatch: low · Streaming: high (state, watermarks)
Use FlinkTrue streaming, complex stateful operators
Use Spark SSMicro-batch, existing Spark ecosystem

HPC & SLURM
Run large ML training and scientific jobs on supercomputing clusters managed by the SLURM scheduler.

HPC Clusters

HPC (High-Performance Computing) clusters are tightly interconnected machines, often with high-bandwidth networking (InfiniBand), shared storage (Lustre/GPFS), and many GPUs per node. Used for ML training, molecular dynamics, CFD simulations.

SLURM Basics

SLURM queues and allocates jobs across nodes. You never run jobs on the login node — submit with sbatch, monitor with squeue, cancel with scancel.

  • sbatch job.sh — submit a batch job script
  • squeue -u $USER — view your jobs
  • sinfo — view cluster partition status
  • scancel <jobid> — cancel a job
  • srun --pty bash — interactive session

Job Arrays & MPI

Job arrays (--array=1-100) run many near-identical jobs with one submission — great for hyperparameter sweeps. MPI (Message Passing Interface) enables multi-node communication for tightly-coupled parallel workloads.

HPC vs Cloud

  • HPC: predictable cost, pre-allocated, fast interconnect, fixed config
  • Cloud: elastic, pay-per-use, slow spin-up, flexible GPU types

Common Directives

--nodesNumber of physical machines
--ntasks-per-nodeMPI ranks / processes per node
--gpus-per-nodeGPU count per node
--memRAM per node (e.g. 64G)
--timeWallclock limit DD-HH:MM:SS
