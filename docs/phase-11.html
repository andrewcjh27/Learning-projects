vLLM & LLM Inference Optimisation
High-throughput LLM serving: PagedAttention, continuous batching, speculative decoding, and quantization tradeoffs.

What is vLLM?

vLLM is a high-throughput LLM serving engine built for production. It achieves 10–24× higher throughput than naive serving by combining several innovations in memory management and batching strategy.

PagedAttention

The KV cache (key-value cache for attention) is the dominant memory consumer during inference. Standard attention allocates a large contiguous chunk per request — most of which is wasted because sequence length is unknown at allocation time. This fragmentation severely limits batch size.

PagedAttention borrows the OS concept of virtual memory paging: the KV cache is divided into fixed-size blocks (pages), allocated on demand. Blocks from different requests can be freely interleaved — no fragmentation, far larger effective batch sizes.

Continuous Batching

Traditional batching waits for all requests in a batch to finish before starting new ones. Continuous batching (iteration-level scheduling) inserts new requests as soon as a slot frees up — dramatically improving GPU utilisation and throughput.

Speculative Decoding

A small, fast draft model proposes N tokens ahead. The large model verifies all N in a single forward pass (parallel). If correct, you get N tokens for the cost of 1 forward pass. Reduces latency without accuracy loss.

Quantization

GPTQ (post-training, layer-wise quantization), AWQ (weight-aware, preserves salient weights). int4 roughly halves VRAM vs fp16 with small accuracy drop; int8 is safer. Throughput vs latency: higher quantization improves throughput but may slightly increase time-to-first-token for large models.

Key metric: Throughput (tokens/sec) measures system capacity; Latency (time-to-first-token) measures user experience. PagedAttention primarily improves throughput by enabling large batches.

Terraform & Infrastructure as Code
Declarative infrastructure management with HCL: plan, apply, destroy, state, and modules.

What is Terraform?

Terraform is a declarative Infrastructure as Code tool by HashiCorp. You describe the desired state of your infrastructure in HCL, and Terraform figures out how to reach it. No more click-ops in the AWS console.

HCL Syntax

Resources are the building blocks. The syntax is: resource "TYPE" "NAME" { ... }

resource "aws_s3_bucket" "data" { bucket = "my-data-lake" }

The Core Workflow

  • terraform init — download provider plugins (AWS, GCP, etc.)
  • terraform plan — preview changes without applying them
  • terraform apply — create/update/delete resources
  • terraform destroy — tear down all managed resources

State File

Terraform maintains a terraform.tfstate file that maps your HCL config to real-world resources. This is how it knows what exists and what needs to change. For teams, store state remotely in S3 + DynamoDB (locking) to prevent conflicts.

Why IaC?

  • Reproducible environments — dev matches prod
  • Version-controlled infrastructure — PRs, code review, audit trail
  • No click-ops drift — the code is the source of truth
  • Modules for reusable infrastructure components

Lesson 03 of 05
Apache Flink & Stream Processing
Stateful stream processing at scale: checkpointing, event time, fault tolerance, and how Flink differs from Spark.

What is Apache Flink?

Flink is a stateful stream processing engine designed for low latency and high throughput. Unlike Spark Structured Streaming (micro-batch), Flink processes events one at a time as they arrive — true streaming with millisecond latency.

Flink vs Spark Streaming

  • Flink: true event-at-a-time streaming, ms latency, rich state management
  • Spark: micro-batch (collect events, process as mini-batch), seconds latency
  • Flink's state is first-class — operators can hold arbitrary state between events

State Backends

HashMap — in-memory, fastest, limited by RAM. RocksDB — spills to disk, handles very large state (TBs), slightly slower.

Checkpointing

Flink periodically saves a consistent snapshot of all operator state to durable storage (S3). A checkpoint barrier flows through the pipeline — each operator saves its state when the barrier arrives. On failure, Flink restores from the last successful checkpoint and replays from there.

Event Time vs Processing Time

Processing time uses the wall clock when the event arrives — simple but incorrect for out-of-order or late data. Event time uses the timestamp embedded in the event itself — correct windowing even for late-arriving data, using watermarks to track progress.

Lesson 04 of 05
Data Contracts
Explicit agreements between data producers and consumers: schema, semantics, SLAs, and ownership in a data mesh world.

The Problem

Data pipelines break silently when upstream teams rename a column, change a type, or drop a field. Consumers only find out when dashboards show wrong numbers — or nothing at all.

What is a Data Contract?

A data contract is an explicit, versioned agreement published by the data producer specifying: schema (field names, types, nullability), semantics (what does revenue mean?), SLAs (freshness, availability), and ownership.

Schema Formats

Common encoding formats: Avro (compact binary, schema in registry), Protobuf (Google, typed, great for gRPC), JSON Schema (flexible, human-readable). Schema evolution rules define backward/forward compatibility.

Semantic Layer & Data Mesh

The semantic layer ensures revenue means the same thing in every dashboard, report, and ML model. In a data mesh, each domain team owns its data as a product and publishes contracts — decentralised ownership with centralised governance.

Tooling

Enforcement tools: Great Expectations (Python, assertion-based), Soda (declarative checks, Soda CL), dbt tests (SQL-level assertions in dbt), OpenMetadata (data catalog with lineage).

Lesson 05 of 05
Fine-tuning & Alignment
When to fine-tune, LoRA vs full fine-tuning, QLoRA, RLHF, DPO, and avoiding catastrophic forgetting.

When to Fine-tune?

Fine-tune when you need: domain-specific vocabulary, consistent output format, proprietary knowledge not in the base model, or a smaller fine-tuned model that beats a larger base model at your specific task (latency + cost win).

Full Fine-tuning vs LoRA

Full fine-tuning updates all parameters — expensive in VRAM and compute, risks catastrophic forgetting (overwrites general capabilities). LoRA (Low-Rank Adaptation) freezes the original weights and trains only two small adapter matrices A and B alongside each layer. The weight update is ΔW = A × B where A is (d × r) and B is (r × d), with rank r ≪ d. Only ~0.1% of parameters are trained.

QLoRA

LoRA applied to a 4-bit quantized base model (NF4 quantization). Enables fine-tuning a 70B model on a single A100 80 GB GPU. The quantized base model is frozen; only LoRA adapters are trained in bf16.

RLHF & DPO

RLHF: train a reward model on human preference data, then use PPO to update the LLM to maximise reward. Effective but complex (requires separate reward model, PPO instability). DPO (Direct Preference Optimisation): skips the reward model entirely — directly optimises the LLM on preference pairs using a closed-form objective. Simpler, often comparable quality.

Avoiding Overfitting

Always validate on a held-out set. Watch for: loss on eval rising while train loss drops (overfit), performance on general benchmarks dropping (catastrophic forgetting). LoRA's small parameter count naturally regularises.
