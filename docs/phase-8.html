Lesson 01
The Modern Data Stack Overview
How data moves from production databases to business dashboards in 2024 — and why ELT replaced ETL.

ELT vs ETL

The old ETL (Extract-Transform-Load) approach processed data before loading it into the warehouse — requiring bespoke transformation pipelines running on separate infrastructure.

Modern ELT (Extract-Load-Transform) loads raw data first, then transforms it inside the warehouse using SQL. Cloud warehouses like Snowflake and BigQuery are cheap to store data in and fast to query, so transforming in-place is both cheaper and simpler.

The standard pipeline

  • Extract + Load — Fivetran or Airbyte pulls data from 200+ sources and loads it raw into your warehouse on a schedule
  • Transform — dbt writes SQL models that turn raw data into clean, business-ready tables
  • Visualise — Looker, Metabase, or Tableau connect to the transformed tables

Medallion Architecture

  • Bronze — raw, unchanged data as ingested (append-only)
  • Silver — cleaned, deduplicated, type-cast data
  • Gold — business-logic aggregations ready for dashboards

The big insight: cloud storage is ~$23/TB/month on S3. It costs almost nothing to keep raw data. So load everything raw first, then transform — you can always re-transform if business logic changes.

Lesson 02
dbt — data build tool
Write SELECT queries, dbt handles the rest. Build a dependency graph of SQL models that transforms raw data into analytics-ready tables.

What is dbt?

dbt lets analytics engineers write models — plain .sql files containing a single SELECT query. dbt materialises each model as a table or view in your warehouse, handling all the DDL (CREATE TABLE AS, DROP, SWAP) automatically.

ref() and the DAG

Instead of hard-coding table names, you use {{ ref('stg_orders') }}. dbt resolves these references to build a DAG (Directed Acyclic Graph) and executes models in the correct order — staging before marts, sources before everything.

Materializations

  • view — default, no data stored, always fresh
  • table — full refresh every run, faster queries
  • incremental — only process new/updated rows using a unique_key
  • ephemeral — like a CTE, never written to disk

Tests

  • not_null — no NULLs in a column
  • unique — no duplicate values
  • accepted_values — column only contains allowed values
  • relationships — foreign key integrity between models

dbt's superpower is lineage: every model knows its parents and children. When something breaks, you can trace it through the graph in seconds.

Lesson 03
Snowflake Architecture
Separated storage and compute, virtual warehouses, Time Travel, and zero-copy cloning — how Snowflake changed data warehousing.

What is Snowflake?

Snowflake is a cloud data warehouse — a managed database built for analytical queries on large datasets. Unlike a database you install and manage yourself, Snowflake runs entirely in the cloud and you query it with standard SQL. You pay only for the storage you use and the compute time you run queries, and scale up or down instantly.

Storage vs Compute Separation

Snowflake stores data on S3 in a proprietary compressed columnar format. Virtual warehouses are separate MPP compute clusters that query that data. You can spin up multiple warehouses for different workloads — one for ETL, one for BI, one for data science — all reading the same data without contention.

Virtual Warehouse Sizes

  • XS / S / M / L / XL — each size doubles the credit consumption and (roughly) halves query time for complex queries
  • Auto-suspend — warehouse shuts down after N minutes of inactivity (typically 1-5 min)
  • Auto-resume — first query wakes the warehouse in ~5 seconds

Key Features

  • Time Travel — query or restore data as it was up to 90 days ago: SELECT * FROM orders AT(offset => -3600)
  • Zero-Copy Clone — clone a table, schema, or entire database instantly with no data copied; clones share micro-partitions until they diverge
  • Micro-partitions — 50–500 MB columnar chunks with automatic clustering metadata for partition pruning
  • Data Sharing — share live data across accounts with no ETL, no data copying

Auto-suspend is the most important cost lever. A warehouse running idle at L size costs ~$16/hour or ~$11,520/month. Suspend after 60 seconds of idle and that drops to nearly zero.

Lesson 04
Airflow Orchestration
Define, schedule, and monitor complex data pipelines as Python-coded DAGs. Never lose a job to a missing dependency again.

What is Airflow?

Apache Airflow is a platform to programmatically author, schedule, and monitor workflows. Pipelines are defined as DAGs in Python — code that describes tasks and their dependencies, not the data itself.

Core Concepts

  • DAG — a Python file defining tasks and their dependencies; scheduled with a cron expression
  • Operator — the unit of work: PythonOperator, BashOperator, S3ToSnowflakeOperator
  • Sensor — a special operator that waits until a condition is met (file appears, external DAG completes)
  • XCom — cross-communication; tasks can push/pull small values (keep under 48KB)
  • Task instance — one run of one task in one DAG run; states: queued, running, success, failed, skipped

Best Practices

  • Idempotent tasks — re-running any task N times produces the same result
  • Atomic tasks — either fully succeed or fail, never partial writes
  • Short-circuit operators for conditional paths that skip downstream tasks
  • SLA miss alerts — get notified when a task takes longer than expected

Managed Airflow options: MWAA (AWS Managed Workflows for Apache Airflow), Cloud Composer (GCP), Astronomer (Kubernetes-native). All eliminate the pain of managing the Airflow metadata DB and workers yourself.

Lesson 05
Star Schema & Analytics Engineering
Design warehouse schemas that are fast to query, easy to understand, and handle historical changes correctly.

Analytics Engineering

Analytics engineering sits between data engineering (building pipelines) and data analysis (running queries). Analytics engineers own the transformation layer — turning raw data into clean, documented, tested models that analysts can trust.

Star Schema

  • Fact tables — records of events (orders, page views, clicks). Append-only, immutable. Contain only foreign keys and measurable facts (amount, quantity, duration)
  • Dimension tables — entities (customers, products, dates). Updated in place or via SCD
  • Grain — the most important design decision: what does one row represent? Define it explicitly before writing DDL

SCD Type 2

Slowly Changing Dimensions track history. When a customer changes their address, instead of overwriting, SCD Type 2 adds a new row with valid_from / valid_to timestamps. The old row's valid_to is set to now, and the new row's valid_to is NULL (or 9999-12-31) for the current record.

Metrics Layer

Define metrics once in code — dbt Semantic Layer / MetricFlow — rather than in every dashboard. Revenue, retention rate, ARPU: defined in YAML, available to all BI tools via a semantic API.

The biggest star schema mistake: putting descriptive attributes in the fact table. Keep facts lean (FKs + measures only). Put customer name, region, segment in dim_customer — that's what dimensions are for.

Question 1 of 4
In the ELT pattern, when does transformation happen?
Before loading into the warehouse (in the pipeline)
During extraction from the source

In ELT, raw data is loaded first — transformation happens after loading, inside the warehouse using SQL (via dbt or similar tools). This is the opposite of old ETL where transformation happened in the pipeline before reaching the warehouse.
Question 2 of 4

Runs the stg_orders model immediately
Creates a dependency so dbt builds stg_orders before the current model
Imports Python functions from stg_orders
Copies data from stg_orders into the current model
ref() tells dbt about a dependency. dbt uses all ref() calls to build a DAG and execute models in the correct order. At runtime, it also resolves to the correct environment-specific table name (dev vs prod schema).
Question 3 of 4
Snowflake's "separation of storage and compute" means:
Data is stored in RAM for speed
You can scale compute up/down independently of how much data you store
Storage is always free
You need separate accounts for storage and queries
Snowflake stores data on S3 (billed per TB) and runs compute on virtual warehouses (billed per credit-second). You can suspend warehouses when idle (cost drops to near zero) while retaining all your data — you only pay for compute when you query.
Question 4 of 4
A fact table's "grain" defines:
The primary key column name
The lowest level of detail one row represents
The number of dimension tables it connects to
The partitioning strategy
The grain is the most critical design decision for a fact table. It precisely defines what one row represents — e.g., "one order line item" vs "one order". All foreign keys and measures must be consistent with the declared grain.
