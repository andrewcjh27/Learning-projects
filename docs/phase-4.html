Lesson 01
SQL Fundamentals
The relational model, query structure, JOINs, CTEs, and window functions — the language every database speaks.

The Relational Model

Data is stored in tables (relations) made of rows (records) and columns (attributes). A primary key uniquely identifies each row. A foreign key references a primary key in another table, creating a link between tables.

Basic Query Structure

SELECT chooses columns, FROM names the table, WHERE filters rows, GROUP BY aggregates, HAVING filters groups, ORDER BY sorts, LIMIT caps results. The database evaluates these in logical order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.

JOINs

  • INNER JOIN — only rows with matching keys in both tables
  • LEFT JOIN — all rows from left, NULLs where no match on right
  • RIGHT JOIN — all rows from right, NULLs where no match on left
  • CROSS JOIN — cartesian product, every combination

CTEs & Window Functions

A CTE (WITH cte AS (...)) names a subquery for readability. Window functions like ROW_NUMBER() and SUM() OVER (PARTITION BY ...) compute per-row results within a group without collapsing rows — unlike GROUP BY.

Indexes

A B-tree index on a column keeps values sorted in a tree structure, turning an O(n) scan into O(log n) lookup. Add an index on any column frequently used in WHERE or JOIN conditions. The tradeoff: indexes consume disk space and slow down writes.

Tip: Use EXPLAIN ANALYZE in PostgreSQL to see whether the query planner uses your index, and how long each step takes.

Choose columns from a table; use * for all columns

Combine rows from two tables on a matching key
WITH cte AS (…)

OVER (PARTITION BY)
Window function: compute aggregate per group while keeping individual rows
CREATE INDEX ON tbl(col)
B-tree index speeds up WHERE/JOIN on that column at the cost of write overhead
Lesson 02
PostgreSQL vs DuckDB
OLTP row-oriented databases vs OLAP columnar engines — choosing the right tool changes query speed by orders of magnitude.

OLTP — PostgreSQL

Online Transaction Processing databases like PostgreSQL are optimised for many small, concurrent reads and writes. They store data row by row — so fetching a single customer record reads exactly one row off disk. Key properties: ACID transactions, referential integrity, concurrent writers.

Best for: application backends, user data, shopping carts, order systems — anything where you read/write individual rows frequently.

OLAP — DuckDB

Online Analytical Processing engines like DuckDB are optimised for full-column scans across millions of rows. They store data column by column — so SELECT SUM(sales) FROM ... reads only the sales column, skipping all other data. DuckDB runs in-process (no server), reads Parquet natively, and can query 500M rows on a laptop.

Best for: analytics dashboards, aggregations, data science, reading Parquet/CSV files at scale.

Why Column Storage Wins for Analytics

A query SELECT region, SUM(sales) FROM orders GROUP BY region only needs 2 of 10 columns. Row store reads all 10 for every row. Column store reads only 2 columns — an 80% reduction in I/O. With compression on homogeneous columns, the gain can be even greater.

Rule of thumb: Concurrent small reads/writes → PostgreSQL. Analytical scans over many rows → DuckDB (or BigQuery, Redshift, Snowflake for cloud scale).

How data physically sits on disk

Both systems have rows and columns. The difference is the physical layout on disk — and that determines what's fast to read.

Row-based (OLTP)
-- Each full row stored together on disk Block 1: [id=1, name="Andrew", revenue=999] Block 2: [id=2, name="Alice", revenue=29 ] Block 3: [id=3, name="Bob", revenue=1497] -- Fetch order #2: read 1 block → fast ✓ -- SUM(revenue): reads ALL blocks — slow ✗
Columnar (OLAP)
-- Each column stored together on disk id block: [1, 2, 3, 4, 5 ...] name block: ["Andrew", "Alice", "Bob" ...] revenue block: [999, 29, 1497, 49 ...] -- SUM(revenue): reads only revenue block ✓ -- 500M rows: 4 GB read instead of 40 GB

How companies use both: The live app writes to OLTP (PostgreSQL) for speed and consistency. A nightly ETL pipeline transforms that data into the wide denormalised format and loads it into an OLAP warehouse. Analysts query the warehouse — never the production database — so reports never slow down the app.

[Your App] → writes to → [PostgreSQL / OLTP]
                              ↓ ETL pipeline (nightly)

OLTP vs OLAP Comparison

Storage layout
Row store: all columns of a row together. Column store: all values of a column together.
Query type
OLTP: point lookups, updates by primary key. OLAP: aggregations across millions of rows.
Concurrency
PostgreSQL: hundreds of concurrent writers. DuckDB: single writer, designed for single-process analytics.
DuckDB deployment
Runs in-process like SQLite — no server, just a library. Reads Parquet, CSV, JSON natively.
ACID transactions
PostgreSQL: full ACID with WAL. DuckDB: ACID within a single connection, not for concurrent multi-user writes.
Lesson 03
Redis
A standalone server that stores data in RAM as key→value pairs — not just a cache, but a speed layer for sessions, leaderboards, rate limiting, and pub/sub messaging.

What is Redis?

Redis (Remote Dictionary Server) is an in-memory key-value store — it holds data in RAM rather than on disk. Every value is stored under a plain string key: key → value. Unlike PostgreSQL, there are no tables, no columns, no SQL — just keys and values, with rich data structure types (strings, lists, hashes, sets) built on top.

It runs as a standalone server process separate from your application. Your app connects to it over a network socket, the same way it connects to PostgreSQL — which means every service and every server in your system talks to the same Redis instance.

In-Memory Speed

Because all data lives in RAM, Redis delivers sub-millisecond latency — typical reads take 0.1–0.5ms vs 1–10ms for a PostgreSQL query. The trade-off: data is bounded by how much RAM you have, and it doesn't survive a crash by default.

Redis vs "a Cache" — what's the difference?

A cache is a concept: store something temporarily so you don't recompute it. Redis is a tool that implements that — plus much more. You could cache results in a Python dict, but that only works on one server. Redis is a separate process every server in your cluster shares.

  • Caching — store an expensive SQL result: SETEX page:/home 60 "<html>..." expires in 60 s
  • Sessions — HSET session:abc user_id 1 name Andrew with TTL so it auto-deletes when you log out
  • Rate limiting — INCR api:user:1 then reject if count > 100; EXPIRE resets the window each minute
  • Leaderboards — ZADD scores 1500 "alice"; ZREVRANK returns rank instantly without sorting a table
  • Pub/Sub — service A publishes an event, service B receives it; Redis is the lightweight message broker in between

Data Structures

  • String — simplest: SET key value / GET key. Stores text, JSON, counters.
  • List — ordered by insertion: LPUSH list val / LRANGE list 0 -1. Good for queues, timelines.
  • Hash — map of field→value: HSET user:1 name Alice age 30. Like a row in a table.
  • Sorted Set — members with float scores, auto-sorted: ZADD lb 1500 "alice". Perfect for leaderboards.

TTL & Expiry

Set a TTL (time-to-live) on any key: EXPIRE session:abc 3600 auto-deletes after 1 hour — no manual cleanup needed. Query remaining time with TTL session:abc.

When Not to Use Redis

Redis is not for data larger than RAM (it's bounded by memory), doesn't support complex joins, and is not a primary database — treat it as a fast temporary layer in front of PostgreSQL.

Cache invalidation pattern: Write to PostgreSQL first, then delete the Redis key (not update it) — the next read will miss and repopulate from the database, preventing stale data races.

Lesson 04
Parquet & Delta Lake
The columnar file format that powers modern data lakes, and the transaction log that turns them into reliable lakehouses.

Apache Parquet

Parquet is a columnar binary file format — data from each column is stored contiguously. This enables column pruning: a query selecting 2 of 8 columns reads only those 2 columns from disk, skipping the rest entirely.

  • Run-length encoding — repeated values (e.g. "US","US","US") stored as ("US" × 3000)
  • Dictionary encoding — low-cardinality columns store an integer index into a small dictionary
  • Predicate pushdown — min/max statistics per row group let the engine skip row groups without reading them

Parquet vs an OLAP Database

Both are columnar — but at different layers. Parquet is a file format (bytes on disk, no query engine). An OLAP database like BigQuery or DuckDB is a full system — it has a query engine, SQL interface, and optimizer. DuckDB can query a .parquet file directly; BigQuery reads Parquet from cloud storage. The same file works with any tool — that portability is the key advantage over a proprietary database.

What is ACID?

ACID is a set of guarantees that make writes reliable. Plain Parquet files have none of these — if a write fails midway, you get a corrupt table. Delta Lake adds ACID via its transaction log:

  • Atomicity — a write either fully commits or fully rolls back. No half-written files left behind.
  • Consistency — every commit leaves the table in a valid state matching the schema.
  • Isolation — concurrent readers see a consistent snapshot; partial writes are invisible.
  • Durability — once the log entry is written, the data survives crashes.

Delta Lake

Delta Lake adds ACID transactions on top of Parquet files via a _delta_log/ transaction log — a series of JSON commit files that record every add/remove/metadata change. Features:

  • Time travel — SELECT * FROM events VERSION AS OF 5 reads any past version
  • Schema enforcement — rejects writes that violate the declared schema
  • OPTIMIZE — compacts many small files into fewer large ones (the "small files problem" fix)
  • Z-ORDER — co-locates related data in the same files for multi-column clustering

Common pattern: Raw data lands as JSON/CSV → converted to Parquet → managed by Delta Lake as a table → queried by Spark or DuckDB.

How Parquet stores data — CSV vs Parquet
CSV — text, row-oriented
# bytes on disk, top to bottom, row by row id,name,country,revenue\n 1,Andrew,US,999\n 2,Alice,US,29\n 3,Bob,KR,1497\n 4,Carol,US,49\n # SELECT SUM(revenue): # must read ALL rows & ALL columns # to find the 4 revenue numbers
Parquet — binary, column-oriented
# bytes on disk, grouped by column [Row Group 1] col id → [1, 2, 3, 4] int32 × 4 col name → dict: {0:"Andrew", 1:"Alice"...} values: [0, 1, 2, 3] # indices, not strings col country → dict: {0:"US", 1:"KR"} run-len: [(0,3),(1,1)] # "US"×3 then "KR"×1 col revenue → [999, 29, 1497, 49] int32 × 4 [Footer] schema · min/max per column # SELECT SUM(revenue): # jump directly to revenue column block # read 16 bytes — skip everything else

Binary means the number 999 is stored as 2 raw bytes (0x03E7), not 3 text characters '9','9','9'. You can't open a .parquet file in a text editor — you need a library (DuckDB, Pandas, Spark) to decode it. The trade-off: files are 5–10× smaller and reads are far faster.

Parquet & Delta Lake Concepts

Column pruning
Skip columns not referenced in SELECT — major I/O reduction for wide tables
Row group
Parquet files are split into row groups (~128MB each); each stores column data + min/max statistics
Predicate pushdown
WHERE date > '2024-01-01' skips row groups whose max date is earlier — no read needed
ACID
Atomicity (all-or-nothing write), Consistency (valid state after every commit), Isolation (concurrent readers see a snapshot), Durability (survives crashes)
_delta_log/
Delta Lake transaction log: each commit is a JSON file listing which Parquet files were added/removed
VERSION AS OF n
Time travel — replay the log up to version n to reconstruct the table at that point
OPTIMIZE + Z-ORDER
Compact small files; Z-ORDER clusters data by multiple columns to speed up multi-predicate queries
Lesson 05
Schema Design
Normalisation, star schemas, foreign keys, and JSONB — structuring data for correctness and query performance.

Normalisation

Normalisation eliminates redundancy by splitting data into related tables. The main forms:

  • 1NF — atomic values in every cell, no repeating groups
  • 2NF — no partial key dependencies (all non-key columns depend on the full primary key)
  • 3NF — no transitive dependencies (non-key columns depend only on the key)

Normalised schemas reduce anomalies: update a city name in one place, not 10,000 rows.

Star Schema

For analytics, normalised schemas require many joins. A star schema denormalises into a central fact table (quantitative events: sales, clicks) surrounded by dimension tables (descriptive context: customer, product, date). Fewer joins, faster analytics.

Foreign Keys & JSONB

Foreign keys enforce referential integrity — you can't insert an order with a customer_id that doesn't exist. PostgreSQL's JSONB column type stores semi-structured data as binary JSON, queryable with data->>'field' syntax — good for flexible, schema-less attributes on otherwise structured rows.

Denormalisation trade-off: Star schemas trade storage space (duplicated dimension data) for query speed (fewer joins). In modern columnar stores, the storage cost is small and the join savings are significant.

Dimension table

Surrogate key

Slowly Changing Dim
Dimension data that changes over time (customer moves city) — handled with versioned rows or effective dates
JSONB

Referential integrity
