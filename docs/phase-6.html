Lesson 01
What is RAG?
Understand why LLMs hallucinate, and how retrieval-augmented generation fixes it without retraining.

The Problem: Frozen Knowledge

LLMs are trained on a fixed dataset — they have a knowledge cutoff. Ask about events after that date and the model confidently makes things up (hallucination). Fine-tuning on new data is possible but expensive and slow.

The Solution: Retrieval at Query Time

RAG (Retrieval-Augmented Generation) keeps the model weights frozen but augments each query with freshly-retrieved context from a document store. The LLM sees the answer before it generates, so it can cite sources rather than invent them.

Three-Step Pipeline

  • Index: split documents into chunks, embed each chunk as a vector, store in a vector DB
  • Retrieve: embed the user query, find top-k most similar chunks via ANN search
  • Generate: pass the chunks + question to the LLM as context in the prompt

vs Fine-tuning: RAG gives up-to-date knowledge and source citations at a fraction of the cost. Fine-tuning bakes knowledge into weights — good for style/skill, bad for facts that change.

Lesson 02
Chunking Strategies
How you split documents dramatically affects retrieval quality — chunk size and boundaries matter.

Why Chunk?

Embedding models have a fixed context window (often 512–8192 tokens). Whole documents rarely fit, and even if they did, a precise question deserves a precise chunk — not a 100-page PDF.

Strategies

  • Fixed-size: split every N tokens. Simple, but breaks mid-sentence — hurts coherence
  • Sentence / paragraph: split on natural boundaries. Better semantic units
  • Recursive character split: tries \n\n, then \n, then space — LangChain's default
  • Semantic: embed sentences, split where cosine similarity drops — expensive but precise

Chunk Overlap

Add 50–100 token overlap between consecutive chunks. Prevents losing context that spans a boundary — a sentence that starts in chunk 3 and ends in chunk 4 is fully covered in both.

Metadata

Attach source, page, section to each chunk. Returned chunks carry this metadata, enabling source citations in the final answer.

Lesson 03
Vector Embeddings & ANN Search
How text becomes numbers, and how vector databases find the closest match in milliseconds.

Text → Vector

An embedding model maps any text to a dense float vector — e.g. 1536 dimensions for text-embedding-3-small. Semantically similar texts produce vectors close together in this high-dimensional space.

Similarity Metrics

  • Cosine similarity: angle between vectors — most common, ignores magnitude
  • Dot product: cosine × magnitude — faster, used in normalised spaces
  • Euclidean (L2): straight-line distance — less common for text

Why Not Exact kNN?

Brute-force nearest-neighbour search is O(n·d) — scanning 10M vectors of 1536 dims each is too slow. ANN (Approximate Nearest Neighbor) algorithms sacrifice a little recall for huge speed gains.

HNSW

Hierarchical Navigable Small World builds a multi-layer graph. Query time is O(log n) — searches 10M vectors in milliseconds. Used by Chroma, Weaviate, pgvector.

Trade-off: ANN may miss the true nearest neighbour 1–5% of the time. For RAG, that's acceptable — you're retrieving top-k candidates anyway.

Lesson 04
Hybrid Retrieval & Reranking
Combine dense vectors with keyword search, then rerank for precision — the production standard.

Dense vs Sparse

Dense retrieval (vector search) excels at semantic similarity — "automobile" matches "car". But it can miss exact keyword matches — product codes, names, rare terms.

BM25 (sparse/lexical) is the gold standard for keyword search — fast, no training required, great at exact matches. Misses paraphrases.

Hybrid Search

Combine both with a weighted sum: score = α·dense + (1−α)·BM25. Typical α ≈ 0.5–0.7. Gets the best of both worlds.

Reciprocal Rank Fusion (RRF)

Alternatively, combine ranked lists: RRF(d) = Σ 1/(k + rank(d)). No score normalisation needed — robust across different score scales.

Reranking

Retrieve top-50 cheaply with hybrid search, then use a cross-encoder (e.g. Cohere Rerank, BGE-Reranker) to score each candidate against the full query. Far more accurate — the cross-encoder sees both query and document together, not just independent vectors.

Why not always rerank everything? Cross-encoders are slow (~50ms/doc). Running them on 10M documents is impractical — that's why we use fast approximate retrieval first, then rerank the shortlist.

Lesson 05
Production RAG
Evaluation metrics, failure modes, orchestration frameworks, and cost optimisation at scale.

The Full Pipeline

  • Chunking pipeline: ingest docs → split → attach metadata
  • Embedding pipeline: embed chunks in batches → store in vector DB
  • Retrieval: embed query → hybrid search → optional rerank
  • Generation: format prompt with context → LLM call → return with citations

Evaluation Metrics (RAGAS)

  • Faithfulness: does the answer follow from the retrieved context? (hallucination check)
  • Answer relevance: does the answer actually address the question?
  • Context precision: are the retrieved chunks relevant?
  • Context recall: do the chunks contain all needed information?

Common Failure Modes

  • Retrieval failure: right answer not in top-k — fix: tune k, improve chunking, add hybrid search
  • Generation failure: LLM ignores context — fix: stronger prompt instruction, smaller context window
  • Chunk size mismatch: too large loses precision, too small loses context

Frameworks & Cost

LangChain and LlamaIndex provide pre-built RAG pipelines. Embeddings are cheap (~$0.02/M tokens); LLM calls are expensive — cache embeddings, batch embed offline, only call LLM at query time.
