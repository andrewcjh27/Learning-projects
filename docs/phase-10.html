Lesson 01 / 05
ML Experiment Tracking with MLflow
Stop losing experiment results. MLflow logs every parameter, metric, and artifact from each training run so you can reproduce and compare.

What is MLflow?

MLflow is an open-source platform for managing the ML development lifecycle. Think of it as a logbook + version control system specifically for machine learning — it records what you tried, what the results were, and lets you compare, reproduce, and deploy the best run.

The Problem Without Tracking

Running experiments without tracking means you can't reproduce results and can't compare runs. "Which hyperparameters gave 94% accuracy last Tuesday?" becomes unanswerable.

MLflow Components

  • Tracking — log params, metrics, and artifacts per run
  • Model Registry — version models, promote to Staging/Production
  • Projects — reproducible ML code via MLproject file
  • Serve — deploy any registered model as a REST endpoint

Key API

  • mlflow.log_param("lr", 0.01)
  • mlflow.log_metric("accuracy", 0.94)
  • mlflow.log_artifact("model.pkl")

Lesson 02 / 05
Docker & Containers
Package your ML app and all its dependencies into a portable image that runs identically everywhere — dev laptop, CI server, or cloud GPU.

What Docker Solves

A Docker image bundles app code + runtime + dependencies. No more "works on my machine" problems. For ML, it means reproducible training and inference across every environment.

Dockerfile Instructions

  • FROM — base image (e.g. python:3.11-slim)
  • WORKDIR — set the working directory inside the container
  • COPY — copy files from host into the image
  • RUN — execute a shell command during build
  • EXPOSE — declare port the container listens on
  • CMD — default command when container starts

Build & Run

  • docker build -t myapp:v1 .
  • docker run -p 8080:8080 myapp:v1

Image layers are cached. Put rarely-changing steps (e.g. pip install) before frequently-changing ones (e.g. copying your source code) to maximise cache hits.

Lesson 03 / 05
Kubernetes Basics
K8s orchestrates containers at scale — handling rolling updates, auto-scaling, and service discovery across clusters of machines.

What is Kubernetes?

Kubernetes (K8s) is a container orchestration platform — it manages running, scaling, and recovering containers across a cluster of machines. Where Docker packages your app into a container, Kubernetes decides where those containers run, how many copies there are, restarts them if they crash, and routes traffic to them. It's the standard way to run production software at scale.

Core Objects

  • Pod — one or more containers sharing networking/storage
  • Deployment — desired state, rolling updates, replica count
  • Service — stable DNS/IP that routes traffic to pods
  • Ingress — HTTP routing rules (host/path → service)

Essential kubectl

  • kubectl get pods
  • kubectl describe pod <name>
  • kubectl logs <pod>
  • kubectl apply -f deployment.yaml

Zero-Downtime Updates

A Rolling Update brings new pods up before old ones go down. HPA (Horizontal Pod Autoscaler) adds replicas based on CPU/memory load.

For ML serving: run multiple model versions as separate Deployments. Use a Service to control traffic split between versions.

Quick Reference

DeploymentManages replica count + rolling updates declaratively
HPAAuto-scales pod count based on CPU/custom metrics

Lesson 04 / 05
CI/CD for ML
Automate everything from code push to production deployment. Every change runs through tests, model validation, and Docker build before it ships.

CI — Continuous Integration

On every pull request: run linting, unit tests, train on a sample of data, and evaluate the resulting model. All automated via GitHub Actions.

CD — Continuous Deployment

When tests pass and the model beats the baseline: build a Docker image, push to registry, deploy to staging, then production.

Model Validation Gates

  • Accuracy gate — must be ≥ baseline on held-out set
  • Data drift check — new training data distribution check
  • Latency benchmark — p99 inference latency ≤ SLA

Blue-Green Deployment

Run old and new model in parallel. Gradually shift traffic (10% → 50% → 100%) while monitoring error rates. Roll back instantly if metrics degrade.

The "Gate Check" stage is the most important safeguard. A model that regresses on accuracy should never reach production automatically.

Lesson 05 / 05
Model Serving & Monitoring
Deploying a model is just the beginning. You need to serve predictions efficiently and detect when the world has changed enough to require retraining.

Serving Options

  • REST API — FastAPI wrapper, ~10ms latency, easy to build
  • gRPC — binary protocol, lower overhead for high-QPS
  • Batch inference — offline, high throughput, no latency SLA
  • vLLM — high-throughput LLM serving with continuous batching

Model Optimisation

  • Quantization — fp16/int8, 2-4× speedup, slight accuracy cost
  • ONNX — framework-independent format, portable inference
  • TensorRT — GPU-optimised inference, fused ops

Drift Types

  • Data drift — input distribution shifts from training data
  • Concept drift — relationship between X and y changes
  • Prediction drift — output distribution changes without new labels

If accuracy on a labelled sample drops below threshold, trigger an automated retraining pipeline. Log every prediction for offline analysis.
