CPU Cores, Threads & Python's GIL
Understand why running more Python threads doesn't speed up your code — and what to do about it.

What is a CPU?

The Central Processing Unit is the brain of a computer. Every line of code you write — Python scripts, SQL queries, data pipelines — gets translated into simple instructions that the CPU executes, one at a time, billions of times per second.

When you run df.groupby('city').mean(), the CPU is what actually does the work: loading data from memory, performing the math, and writing the result back. Understanding it explains why some code is fast and other code is slow.

A CPU sits on the motherboard and connects to RAM (temporary fast storage), storage (SSD/HDD), the GPU, and all other hardware. It is the coordinator of everything.

What is a CPU Core?

A core is a complete, independent processor inside your CPU. Each core can execute one stream of instructions at a time. A modern laptop has 8–16 cores; a cloud server might have 96.

What's inside a core — Units

A core isn't just one thing. It contains several units, each doing a different job:

  • Fetch Unit — grabs the next instruction from memory
  • Decode Unit — figures out what that instruction means
  • ALU (Arithmetic Logic Unit) — does the actual math: +, −, ×, comparisons
  • Memory Unit — reads and writes data to/from RAM
  • Branch Predictor — guesses which way an if/else will go, pre-fetches early

These units run in a pipeline — while the ALU executes instruction 3, the Decode Unit is already decoding instruction 4, and the Fetch Unit is already grabbing instruction 5.

Hyper-threading

When a thread tells the Memory Unit to load data from RAM, the Memory Unit spends ~80 ns waiting for that data. During that wait the ALU, Fetch, and Decode units sit idle — nothing to do.

Hyper-threading lets a second thread on the same core use those idle units during the wait. The other physical cores stay completely idle — this is purely a within-one-core optimization that gives ~20–30% more throughput.

Python's GIL — Why it exists

Python tracks memory via reference counting — every object has a counter of how many variables point to it. When the count hits 0, Python deletes it.

The problem: two threads can read and write the same counter simultaneously — a race condition. Both threads read count=5, both add 1, both write 6. Result should be 7. This causes memory leaks or crashes.

Python's fix in 1991: one lock, one thread at a time. The GIL ensures only one thread touches Python objects — no two threads can ever corrupt the same reference count.

This is why threading your pandas code doesn't make it faster. Use multiprocessing instead — each process has its own separate memory and its own GIL.

Why hasn't the GIL been removed?

Every C extension ever written (numpy, pandas, scikit-learn…) assumes the GIL exists. Removing it safely took decades. Python 3.13 (2024) finally shipped an experimental free-threaded build — opt-in and still early.

How NumPy still uses multiple cores

CPython (the Python you install) is itself written in C. NumPy is also written in C under the hood. When you call np.dot(a, b), Python hands the work to a pre-compiled C routine that works directly on raw memory buffers — no Python objects, no reference counts.

Because that C code doesn't touch Python objects, numpy releases the GIL before entering the C routine, then re-acquires it when done. While the C math is running, other threads are free to run their own C code simultaneously.

The boundary that matters:

  • Your Python code (loops, if/else, custom functions) → GIL held → one thread at a time
  • C extension code (numpy math, pandas sort, etc.) → GIL released → multiple threads can overlap

Lesson 2 of 5
The Cache Hierarchy
Why the same piece of data can take 0.3 ns or 10 ms to access — and how this shapes every data tool you'll use.

What is RAM?

RAM (Random Access Memory) is your computer's short-term working memory. When you open Python and load a CSV file, the data lives in RAM while your script runs. It's fast, but it's temporary — everything in RAM disappears when you turn off the computer.

Your laptop likely has 8–32 GB of RAM. A cloud server can have hundreds of GB. When a pandas DataFrame is "in memory", it literally means it's sitting in RAM.

What is a Cache?

A cache is a small, extremely fast storage layer that sits between the CPU and RAM. Its job is simple: keep a copy of the data the CPU is most likely to need next, so the CPU doesn't have to wait for the slower RAM every time.

Think of it like a physical desk. Your RAM is a filing cabinet across the room — slow to walk to. Your cache is the papers sitting right on your desk — instant to grab. The CPU always checks the desk first before walking to the cabinet.

Why does the CPU need a cache at all?

The CPU can execute billions of operations per second. RAM can only deliver data at a fraction of that speed. Without cache, the CPU would sit idle waiting for RAM most of the time. Cache bridges that speed gap — it stores recently and frequently used data close to the core so the CPU rarely has to wait.

The hierarchy — L1, L2, L3

There isn't just one cache — there are three layers, each a different trade-off between speed and size:

  • L1 — smallest (~32 KB), fastest (~1 ns), sits directly inside each core
  • L2 — medium (~256 KB–1 MB), slightly slower (~4 ns), still per-core
  • L3 — largest (~8–64 MB), slowest of the three (~25 ns), shared across all cores

The CPU checks L1 first. If the data isn't there (cache miss), it checks L2, then L3, then finally RAM. Each step is slower than the last. A miss all the way to RAM wastes hundreds of CPU cycles just waiting.

Cache hit vs cache miss

A cache hit means the CPU found the data it needed in cache — fast, no waiting. A cache miss means it wasn't there — the CPU must fetch from the next level down, stalling while it waits. Writing code that causes many cache hits is called having good cache locality and is one of the biggest practical performance optimizations.

What is a cache line?

When the CPU needs one value from RAM, it doesn't fetch just that one value — it always grabs 64 bytes at a time. That 64-byte chunk is called a cache line.

Why 64 bytes? Because if you needed the value at position 10 in an array, you'll almost certainly need position 11, 12, 13 next. So the CPU pre-loads the whole neighbourhood. If your next values are within the same 64 bytes — they're already in cache, free. If your data is scattered all over memory — every access triggers a new 64-byte RAM trip.

Why Parquet & DuckDB win at analytics

The connection to cache lines is direct. Imagine a table with 5 columns: id, name, city, salary, date.

A row store (MySQL) keeps all columns of each row packed together in memory:
[id][name][city][salary][date] [id][name][city][salary][date]…
One 64-byte cache line loads parts of a row — mostly id, name, city, date — columns you never asked for. The salary values are scattered, each one forcing a new cache line load.

A column store (DuckDB, Parquet) keeps all values of each column together:
[salary][salary][salary][salary][salary][salary][salary][salary]…
One 64-byte cache line loads 8 salary values at once (8 bytes each). Every byte loaded is exactly what you asked for — zero waste.

For AVG(salary) across 1 million rows: the column store loads ~50× less data and keeps the cache full of only the values it needs. That's why DuckDB, Snowflake, BigQuery, and Parquet are 10–100× faster for analytics.

Memory Latency — The Speed of Everything
Visualize why in-memory databases exist, why Redis is fast, and why network calls are expensive.

Latency vs. bandwidth

Latency is the delay before data starts arriving. Bandwidth is how much data arrives per second. You can have high bandwidth with high latency (bulk transfer) or low latency with low bandwidth. For interactive systems, latency is usually the bottleneck.

The human analogy

If L1 cache access = 1 second, then:

  • L2 = 4 seconds
  • L3 = 40 seconds
  • RAM = 1.5 minutes
  • NVMe SSD = 3 days
  • HDD = 11 months
  • Network (WAN) = 100+ years

Why Redis exists

A PostgreSQL query hitting disk = milliseconds. Redis in memory = microseconds. For hot data (sessions, counters, leaderboards), the 1000x latency difference matters enormously.

Why Spark uses RAM

Hadoop MapReduce wrote intermediate results to disk between steps. Spark keeps them in RAM. That's why Spark is typically 100x faster than MapReduce — it avoids disk I/O entirely for iterative workloads.

Row vs Column Storage
The architecture choice behind why DuckDB, Snowflake and Parquet are so much faster for analytics.

Row stores (OLTP)

Traditional databases (MySQL, PostgreSQL in row mode) store data row by row. Inserting or updating a record is fast — all fields for a row are together. Perfect for transactional workloads (e-commerce, banking).

Column stores (OLAP)

Columnar databases store all values of a column together. When you do SELECT AVG(salary), you read only the salary column — not the name, city, or any other field. 10–100x less I/O for analytical queries.

Compression

Columnar data also compresses far better. A column of cities might have thousands of repeated values like "NYC". Run-length encoding can compress that to near zero. A row store mixes types, making compression less effective.

When to use what

  • Row store: OLTP — inserts, updates, point lookups by ID
  • Column store: OLAP — aggregations, scans, analytical queries
  • Parquet: columnar file format — the lingua franca of data lakes

Snowflake, DuckDB, BigQuery, Redshift — all columnar. This is why they can query billions of rows in seconds.

CPU vs GPU Architecture
Why deep learning needs GPUs, what CUDA is, and when a GPU actually helps you as a data engineer.

The fundamental difference

A CPU has 8–96 powerful cores — each can handle complex logic, branching, and diverse tasks. A GPU has thousands of tiny cores — each is simpler, but they all run simultaneously.

Think CPU = a few expert surgeons. GPU = tens of thousands of factory workers doing one repetitive task in parallel.

Embarrassingly parallel problems

Matrix multiplication (the core of neural networks) is embarrassingly parallel — every output element is independent. A 1024×1024 matrix multiply has ~1 million independent operations. A GPU can do them all at once.

CUDA

CUDA is NVIDIA's parallel computing platform. When you run a PyTorch model on a GPU, CUDA launches thousands of threads on the GPU cores to compute matrix operations in parallel. You don't write CUDA directly — PyTorch and NumPy handle this.

VRAM — the constraint

GPU memory (VRAM) is separate from system RAM. A model must fit in VRAM to run on GPU. An RTX 4090 has 24 GB VRAM. LLaMA 70B needs ~140 GB — it needs multiple GPUs or quantization.

When GPU helps in data engineering

  • Model training — always GPU
  • Batch inference — GPU if throughput matters
  • RAPIDS cuDF — GPU-accelerated pandas replacement
  • SQL on GPU — BlazingSQL, OmniSci
  • Traditional ETL — usually CPU is fine
